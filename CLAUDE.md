# CLAUDE.md — vehicle-rt-core

@.claude/PLATFORM-RULES.md

## What this repo is

The main domain controller firmware running on the **Cortex-M7 core of the STM32H755** (NUCLEO-H755ZI-Q, D-072); the Cortex-M4 of the same chip is the safety partition (`vehicle-safety-node`), reached only through an E2E-checked inter-core mailbox, and rt-core never drives the LED ring or the mirror LEDs (D-041). Power management and park mode (from the retired io-node) also live here. CAN read/write, telemetry collection, logging, sensor fusion, UDS/ISO-TP/bootloader, XCP calibration, cornering safety EKF estimation, context classification, virtual dyno computation, the anomaly score's ESP safety-net rules (see below) — all of it lives here, as separate modules under `features/`.

## Directory structure (layered architecture — do not mix)

```
/src/hal/         → hardware abstraction (CAN, IMU, GPS, sensors)
/src/services/     → signal pool, logging manager, EKF fusion, time base
/src/features/      → independent function modules (listed below)
```

Modules under `features/` **do not know about each other**, they only look at `services/`. If you delete a module, the others must keep working. Do not break this rule when adding a new feature.

### Modules under features/ (current plan)
- `uds/` — UDS server + client, ISO-TP transport layer
- `bootloader/` — OTA, A/B bank, rollback
- `xcp/` — calibration interface
- `heartbeat/` — rt-core's 0x081 heartbeat (D-064)
- `cornering/` — **ONLY Layer 2 (EKF estimation): µ, mass, center of gravity, lean angle.** Clipped to physical ranges, published over CAN. Deterministic decision/warning/LED triggering is NOT HERE — that's in `vehicle-safety-node`, isolated. Don't break this separation; rt-core never makes the cornering-warning decision, it only feeds parameters.
- `dyno/` — virtual dynamometer
- `context/` — context classification (road type, surface, riding event) — the producer of the context data bus
- `anomaly-safety-net/` — **NOT ML**, just a handful of fixed rules (engine temperature threshold, RPM spike, etc.). The actual anomaly model lives on the Raspi (`vehicle-linux-node`); this is only a guarantee that things don't drop to zero if the Raspi crashes. Don't make this heavier — staying rule-based is a deliberate decision.

## SAFETY-CRITICAL RULES (never violate, no exceptions)

1. `cornering/` (EKF estimation only, in this repo) never makes a cornering-warning/LED decision — that decision lives in `vehicle-safety-node`. This repo only computes µ/mass/lean angle and publishes it to CAN.
2. This repo NEVER writes to the ECU (engine control unit) in any way; the ECU is read-only (D-037). rt-core is the **only** tester on the vehicle bus (FDCAN1, D-021): it polls the DIDs in `uds/vehicle_cl250.yaml` and sends only what that file's `tester_policy` allows (D-020; session control 0x01/0x03 only). The policy may only be narrowed; widening it or codegen's golden copy (D-027) needs the user's approval. Everything goes through the generated `vehicle_cl250_request_allowed()` / `vehicle_cl250_frame_allowed()` gates and the fixed `can_if` guard. It republishes decoded vehicle signals on the platform bus. The UDS **server** runs only on the platform bus (FDCAN2) (own DIDs, DTCs, bootloader). If a task would widen this boundary, don't do it; ask the user.
3. Dynamic memory allocation (`malloc`/`new`) is not used on safety-critical paths (`cornering/` decision layer, watchdog) — static/stack allocation is preferred. Full MISRA-C compliance is the goal, but this is the minimum rule.
4. Interference independence: a delay/crash in a low-priority module like `anomaly-safety-net/` must NEVER affect the timing of the `cornering/` decision loop — set up task prioritization accordingly.
5. Messages sent to the safety node (platform CAN 0x010-0x07F) and the heartbeat are E2E-protected (D-005); E2E functions come from `gen/`, never hand-written.

## Dependencies

Reads signal/UDS definitions from `vehicle-defs` (submodule: `external/vehicle-defs`, pinned to a tag; generated code at `external/vehicle-defs/gen/c/<node>/`). Bridges to `vehicle-connectivity-node` (ESP32-S3) via SPI/UART.

## Build

CMake + STM32CubeMX (HAL) + arm-none-eabi-gcc (D-007). RTOS: FreeRTOS/CMSIS-RTOS2 (D-012). Target: STM32H755 Cortex-M7 (D-072; flash bank 1, the M4 owns bank 2).
- `cubemx/` is generated code — only write into `USER CODE` blocks.
- Pure logic (EKF, ISO-TP, UDS state machine, E2E, dyno) is written without a HAL dependency and tested under `tests/host/` with Unity. This plus Renode is the path forward while there's no H7 hardware.
- Skeleton: `/repo-bootstrap`; new feature: `/feature-module`.
- Commands (CMake >= 3.20 + Ninja; `git submodule update --init` first, defs pinned to the tag in `vehicle-workspace/manifest.yaml`):
  - `cmake --preset host-tests && cmake --build --preset host-tests && ctest --preset host-tests` (Unity, ASan + UBSan, plus the 2 s SIL smoke run and the `--uds-scenario` UDS server run)
  - `cmake --preset host-tsan && cmake --build --preset host-tsan && ctest --preset host-tsan` (ThreadSanitizer: the snapshot/alive/IMU tests, including the two-thread stress tests of the snapshot and of the lean link)
  - SIL program (D-034): `build/host-tests/src/vehicle_rtcore_host` (in-process bus + simulated CL250 ECU); on Linux `--vcan vcan0`
  - `cmake --preset target-m7-debug && cmake --build --preset target-m7-debug` (also `target-m7-release`); `-DARM_TOOLCHAIN_DIR=...` if `arm-none-eabi-gcc` is not on PATH
- The target presets cross-compile only the pure logic (`vehicle_rtcore_logic`) for Cortex-M7 (flags shared by the H7 Cortex-M7 parts). The board is the NUCLEO-H755ZI-Q (D-072): the dual-core CubeMX project, startup, linker script, MPU, clock and option-byte init follow D-072 item 4 and are red-zone, invariant-8 code.
- Current modules and layers:
  - `features/uds/isotp_core` (ISO-TP, Ç2)
  - `features/uds/isotp_link`: the core on a port + ID pair. `isotp_link_open_vehicle_cl250()` is the only vehicle-port link and takes its IDs and padding from gen/.
  - `features/uds/uds_client` + `uds_client_core` (Ç3): the single read-only vehicle tester. It keeps the session (0x10 03, 0x3E 80) and polls the gen/ DIDs into `services/vehicle_signals`, the gen/ `priority` first (D-043); a DID whose last read timed out, or whose last answer came later than its period, competes as normal with no NRC 0x78 extension until it answers in time or is skipped (D-050, D-051); a sample is stamped with the send time of its DID's oldest unanswered read (D-051). Requests are Single Frames; a segmented answer gets the one gen/ FC.CTS only while the link expects the answer to its own allowed request, once, FF_DL <= 64 for a read (D-059; the RX buffer is 255 B since D-080) and is then "service unavailable" for a table DID. D-080: when no DID is due it reads the ECU's DTC freeze frames (0x19 count, list, 0x04/0x06 per DTC, at most 8 DTCs / 18 requests per run) at key-on and at warm idle, FF_DL <= 255 with the FC only for a First Frame that echoes `59 <sub> <DTC>`, and hands the raw answers to a sink before the buffer is released; some failures turn 0x19 off for the stop epoch (`features/uds/README.md`). Fail-closed latch with a reason (`uds_client_fault()`: gate, guard, or a second tester seen on the request IDs or the gen/ OBD functional watch IDs). ISO 14229 codes come from gen/ `uds_iso14229.h`.
  - `features/uds/dtc_snapshot_core` (D-080): the pure run state machine of the 0x19 DTC freeze-frame reader (count, list, snapshot, extended data; run and epoch budgets; halts), called only by `uds_client_core`. It builds requests from gen/ only, never 0x14, and stores a DTC only from a length-checked 0x02 answer.
  - `features/uds/uds_server` + `uds_server_core` (Ç3, D-040): rt-core's diagnostic server on the **platform bus only** (0x710/0x718, functional 0x7DF): 0x10 / 0x3E / 0x22 / 0x19 / 0x14, NRCs, P2 / P2* / S3, all from gen/ `platform_uds.h`. It serves the 0xFD02 health DID (D-055: step counters from `services/diag`, per-port CAN state from `services/can_sm`, UNKNOWN when not known), the 0xFD03 `LEAN_HEALTH` DID (D-067, E-17 (a): from `services/lean_health`, the comms task's copy of the EKF's last lean record; the server never reads the lean snapshot) and reports DTC U0001-88 while the vehicle port is latched. It never touches the vehicle port and never includes `uds_client.h`.
  - `features/vehicle_republish` (ISSUES D-5, D-056): republishes `services/vehicle_signals` on the platform bus as gen/ 0x021 `VehicleSpeed` (E2E, dedicated replace-on-new TX buffer; not a safety-node input, D-041/D-048) and 0x110 `VehicleEngine` (Tx FIFO), each at its gen/ cycle time. NONE/STALE/out-of-range samples go out INVALID with value 0 (no clamping), and the speed AGE saturates at 2550 ms when INVALID. The E2E counter advances only with accepted frames. It runs in `comms_pass()` after the platform dispatch and before the UDS server.
  - `features/heartbeat` (D-064): rt-core's gen/ 0x081 `HeartbeatRtCore` every 100 ms (E2E, dedicated replace-on-new TX buffer), the input of safety-node's D-042 fallback. NODE_MODE: INIT for the frame of the first step, DEGRADED while a DTC monitor's last result is failed or its condition holds unmonitored (vehicle tester latched or not running, vehicle port latched), else NORMAL; also DEGRADED while a registered EKF is stalled, never ran or has no open lean sender (`ekf_stalled` from `app/comms`, D-064 item 4; the lean link's counter is registered at boot, D-065 PR 3b). ERROR_COUNT: DTC failure onsets since boot; UPTIME: never decreasing seconds. Runs in `comms_pass()` after the republisher, before the UDS server.
  - `features/cornering/lean_core` (D-065 item 1, PR 2): the pure 2-state roll EKF over [roll, roll-rate gyro bias]. It predicts with the body x gyro and measures the body z gyro against h = (g/v)·sin(roll), the coordinated turn at pitch 0. v is the speed's upper bound (sample + age × margin, so a stale speed makes the lean err high; user). R adds a turn-in lag term, and the bias is frozen above 10°/s of roll rate. Without a speed the roll falls back to its prior; |roll| ≥ 90° restarts the filter. The gyro rates must be means over the sample interval (services/imu contract). Float32, `isfinite` on every input and on the state, `-fno-math-errno`, never `-ffast-math` (the file refuses to build otherwise). The speed comes in as physical value, absolute stamp and state; the core computes its age every step (≤ 300 ms plus age × 5 m/s², a future stamp is never a wrapped age), and without a usable speed the lean is INVALID. An innovation gate: a reject run longer than 100 ms means diverged, so INVALID and reinit; while a run is open QUALITY is capped at 50 (user). QUALITY comes from the roll σ. INVALID always carries roll 0 and QUALITY 0. It never produces CLAMPED: the PR 3 glue clamps only the returned copy. Constants are provisional until T1/T4. Called only by the `lean` glue.
  - `features/cornering/lean` + `lean_tx` + `lean_tx_core` (D-065 item 2, PR 3b; cornering README "Lean glue"): `lean_link_t` carries the speed (comms → EKF) and the output (EKF → comms) through two `services/snapshot`s plus the EKF alive counter. `lean_ekf_step()` (EKF task, 20 ms, highest task priority, WCET budget 1 ms; user) reads the speed, drains `services/imu` with the standstill flag (VALID 0 km/h, ≤ 200 ms old, previous sample also 0), steps the core only for a new VALID sample, publishes, then bumps alive; after a snapshot producer fault it never writes that slot again. `lean_tx` (comms task) hands the 0xF40D speed over (VALID only inside the gen/ 0x021 range) and sends 0x020 at its gen/ cycle through `services/com` (dedicated buffer, E2E counter committed on `CAN_PORT_OK` only). `lean_tx_core` (pure) builds 0x020: snapshot fault → output age ≤ 35 ms (a stamp ≤ 10 ms ahead is age 0) → state switch → finite roll < 90° and QUALITY range → clamp the copy to gen/ ±55° as CLAMPED; any failure is INVALID with LEAN 0 and QUALITY 0.
  - `features/derived` (D-070, C3 part 1): derived signals of class A that read DIDs only (28 of catalog section 5: gearbox ratio and gear, acceleration and jerk, trip distance/time, idle time, torque and power, air density, AFR and fuel formulas, residuals, altitude, coolant/oil rate, `stop_event`), computed on the gen/ period grid with sample-and-hold ages. `derived_core` (pure) + `derived_gear` + `derived_ride` (class-B ride summaries, part 2a: 12 scalar signals per D-075 stop epoch = D-087 ride, `derived_ride_get(CURRENT|PREVIOUS)`, no DID/CAN/persistence yet) + `derived` glue; the computed set is decided from the gen/ table; a result outside the gen/ range is invalid, never clamped. QM information: never feeds 0x020, safety-node, the heartbeat or the safety net (CI greps that the safety-relevant modules and `app/comms` do not include it). It runs in its own task below the comms task and reads the DIDs only through `services/derived_inputs`. Verified against the vehicle-server golden vectors (`features/derived/README.md`).
  - `services/derived_inputs`: the comms to derived task DID hand-over on `services/snapshot` (one producer call in `comms_pass()`, the last call of the pass, one consumer call in `features/derived`); its record also carries the tester epoch.
  - `services/tester_epoch`: the UDS client's D-075 stop epoch (`{open, counter}`) written by the client glue and read by `derived_inputs_publish()`; it is the ride boundary of the derived class-B summaries (D-087).
  - `services/diag`: DTC memory (RAM, level-triggered), the vehicle-tester status and the client's step counters (fresh within 500 ms, D-055); the client glue writes them, the server reads and clears the DTCs and reports its own monitors. Each monitor's last result and the onset count are kept apart from the status bytes (a 0x14 clear changes neither; D-064, the heartbeat). It includes no other service.
  - `services/com` + `com_core` (D-056 item 7): the shared cycle grid and platform send path (`com_send()`: OK / TX_FULL retry / drop) of the republisher and the heartbeat; the senders keep their E2E state.
  - `services/timebase` (task-safe, `hal/hal_time.h`)
  - `services/snapshot` (D-065): the SPSC triple buffer between tasks of different priority; index-only, no lock/wait/retry (never a seqlock). Atomics behind `hal/hal_atomic.h`.
  - `services/alive` + `alive_core` (D-064 item 4, D-065): a task's lock-free alive counter and the supervisor's pure stall monitor (baseline at registration, never-ran = stalled, sticky).
  - `services/imu` + `imu_core` (D-065 PR 3a): the EKF task's IMU input. Drains the `hal/imu.h` FIFO once per EKF period (bounded, a backlog is flushed) and returns the gyro rates as the mean over the period, never a point sample (aliasing). Stale, saturated, lost, unconfigured and first periods are INVALID. The z offset is learnt at standstill (2 s, x/y/z means within 1 deg/s, offset at most 2 deg/s, relearnt at every stop; user); until the first learn every sample is INVALID. EKF task only; called by `features/cornering/lean`.
  - `services/vehicle_signals`: the last raw/physical sample per gen/ DID. VALID/STALE is derived at read time from `stale_after_ms`.
  - `services/can_if`: CAN RX routing, plus the **fixed, fail-closed D-020 vehicle-bus guard** that every vehicle frame passes. Never add a bypass. A bus-off or latched port refuses writes with `CAN_PORT_ERR_IO` (not a guard refusal); `can_if_apply_filters()` turns the receiver table into the port's acceptance filters, after handing the port its dedicated replace-on-new TX IDs (`can_if_register_tx_dedicated()`, platform port only, D-056).
  - `services/can_sm` + `can_sm_core` (Ç1): CAN error state machine per port (error active/passive/bus-off, backoff recovery, N_As abort). The vehicle port latches on its 5th bus-off (D-030, D-054); the platform port never latches. `can_sm_state_known()` tells a read state from an unknown one (D-055).
  - `app/comms`: the portable comms pass (client, the speed hand-over to the EKF, then the republisher, the heartbeat and 0x020, then the server), shared by the host program and the future H7 task. It owns the EKF alive supervision (`comms_ekf_t`: zeroed = no EKF; NULL reads as stalled; so does a registered EKF whose lean sender is not open, D-086) and passes `ekf_stalled` to the heartbeat. `comms_open_lean()` opens 0x020 only for the registered counter of that lean link (D-065 amendment); in the pass, an open lean link under another supervision sends no 0x020 and reads as a stalled EKF.
  - `hal/can_types.h`, `hal/can_port.h` (services and app only; FDCAN requirements in `hal/README.md`), `hal/hal_time.h`, `hal/hal_atomic.h` (services only; H7 requirements in `hal/README.md`), `hal/imu.h` (`services/imu.c` only; H7 IMU requirements in `hal/README.md`), and the host port `hal/host/` (including the IMU FIFO fake `imu_host`)
- Libraries:
  - `vehicle_rtcore_logic` (pure) and `vehicle_rtcore_fw` (services + feature glue, HAL interfaces only) are also cross-compiled for M7.
  - `vehicle_rtcore_hal_host` and `vehicle_rtcore_host` build natively only.
