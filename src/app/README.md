# src/app

Task and loop setup. Module periods and priorities are registered here, with the rationale for safety-relevant ones (freedom from interference).

- **`comms` (Ç1, portable):** `comms_pass(client, server, republisher, heartbeat, ekf)` is the fixed order of rt-core's CAN work, for the host program and the H7 comms task alike: `can_sm_step(VEHICLE)`, `can_if_dispatch(VEHICLE)`, `uds_client_step()`, then `can_sm_step(PLATFORM)`, `can_if_dispatch(PLATFORM)`, `vehicle_republish_step()`, `heartbeat_step()`, `uds_server_step()`, and last `derived_inputs_publish()`. One task runs both UDS roles, the republisher and the heartbeat, the client first (uds README, MINOR-3 and MINOR-C; the republisher's place: D-056 item 4; the heartbeat's: same reasons, `features/heartbeat/README.md`). `comms_apply_filters()` sets both ports' acceptance filters (and the platform port's dedicated TX buffers) once the client, the server, the republisher and the heartbeat opened. It includes services and feature headers only, never `hal/`.
  - **EKF alive supervision (D-064 item 4, D-065 item 2):** `comms_ekf_t` belongs to the comms task. Zeroed (`comms_ekf_init()`) it means "no EKF": `ekf_stalled` is false and nothing changes. `comms_ekf_register(ekf, counter)` (boot, D-065 PR 3) takes the EKF task's `alive_counter_t` with its current count as the baseline; from then on every pass samples it before `heartbeat_step()` and the heartbeat reads DEGRADED while the count never changed or did not change for more than `COMMS_EKF_ALIVE_WINDOW_MS` (gen/ `PLATFORM_EKF_LEAN_E2E_TIMEOUT_MS`, static-asserted ≥ 2 EKF cycles). A NULL `ekf` reads as stalled. 0x020's sender opens only when `comms_ekf_registered()` (fail closed). The counter is the only state the comms task shares with the EKF task, through `hal/hal_atomic.h` (no lock). **DID 0xFD03 (E-17 (a), D-067):** after `lean_tx_step()` each pass hands `services/lean_health` the comms-side flags (the two comms snapshot latches and `EKF_ALIVE_OK` = registered AND the heartbeat's own stalled verdict clear) right before `uds_server_step()`; see `features/cornering/README.md`.
  - **Derived-signal hand-over (D-070, C3):** `derived_inputs_publish(timebase_now_ms())` is the comms task's one producer call for the derived task: as the last call of the pass (after `uds_server_step()`, so no frame work waits for it; nothing later writes `vehicle_signals`) it copies the DID samples the client wrote in this pass into a snapshot (bounded, no lock, no wait). Only `features/derived` reads it, from its own lower-priority task; nothing in the pass depends on that task. Before `derived_inputs_init()` (boot, before the tasks) it does nothing but count (`derived_inputs_skipped_count()`), so a missing boot call on the H7 is visible. The same record carries the tester's stop epoch (`services/tester_epoch`: open flag and counter), the ride boundary of the class-B summaries (D-087 item 2); the comms pass order is unchanged, only the UDS client glue writes `tester_epoch_set()` at the end of its step. A producer fault latches and stops the publishing; `test_derived_inputs_fault` and `test_comms_derived` show 0x081 and 0x020 keep their frame counts and longest gap with derived_inputs never initialised, healthy, or faulted. **Cost:** measured on the host, 40 `vehicle_signals_get()` plus the copy and one atomic exchange take about 115 ns per publish (`-O2`, Apple arm64, 1e6 calls); the target figure comes from the DWT cycle counter when the board exists (D-070 item 6). `comms.c` includes only the service, never `features/derived` (CI).
- **`host/` (D-034):** `vehicle_rtcore_host`, rt-core as a host program (SIL). It runs the same `services/` and `features/` code as the target. One pass per ms: the simulated peers answer what rt-core sent in the last pass, then the EKF step and `comms_pass()`, then `derived_step()` (D-070; the derived task is below the comms task). In this sequential host loop the client's step-gap statistics (D-053) include `derived_step()`, which on the H7 runs in its own task and does not widen the gap. The summary prints each port's state, bus-offs, recoveries, N_As aborts and blocked writes.
  - Default: in-process bus plus `sim_ecu`, a minimal simulated CL250 ECU. It answers 0x10 01/03, 0x3E and 0x22 from the gen/ DID table, and here it needs the extended session for its reads, like the real ECU (D-019). Tests also use its fault hooks: silent, NRC 0x78 bursts, a segmented answer, a fixed NRC, and a session drop. It stands in until the vehicle-hil-bench live model exists (D-035).
  - `--vcan IF` (Linux): the vehicle port on SocketCAN, with an external peer. Interfaces not named `vcan*` also need `--allow-real-bus`, because a second tester next to a real rt-core would break D-021. The `can_if` vehicle guard applies either way.
  - The loop runs the UDS client (`features/uds/uds_client`, Ç3): session, tester present, and the gen/ DIDs into `services/vehicle_signals`. Once a second it prints the signal table (raw, physical, age, VALID/STALE).
  - The platform port is always an in-process bus. The UDS server (`features/uds/uds_server`, Ç3, D-040) runs on it. With `--uds-scenario`, `sim_tester` (a scripted platform-bus tester) runs a full diagnostic session: session, multi-frame multi-DID read, DTC count/list/clear, functional requests, NRCs, the P2 check and S3 expiry. The program exits 0 when every step passes (ctest `sil_vehicle_rtcore_host_uds_server`, about 6 s).
  - The republisher (`features/vehicle_republish`, D-056) sends 0x021 and 0x110 on the platform bus; `sim_listener` checks every 0x021 with the receiver E2E check, the frame lengths and the longest gap of both, and the summary prints them.
  - The heartbeat (`features/heartbeat`, D-064) sends 0x081; `sim_listener` checks every frame with the receiver E2E check (as SAFETY would), NODE_MODE (INIT only first, then NORMAL or DEGRADED), that UPTIME never decreases and that no gap reaches the 300 ms E2E timeout. rt-core's gen/ has no unpack for its own message, so `sim_listener_heartbeat_decode()` locates each field bit with the gen/ pack function (no hand-written layout). The demo fails otherwise.
  - With `--duration-ms N` it exits 0 when at least `--min-responses` DID reads were decoded, the client did not latch as failed and the listener passed (ctest `sil_vehicle_rtcore_host_demo`: 2 s, 20 reads, 40 frames of each message with E2E OK).
- **Target:** FreeRTOS/CMSIS-RTOS2 tasks (D-012), called from the CubeMX `USER CODE` blocks. Empty until the CubeMX project exists. The comms task calls `comms_pass()` every 1 ms; its period plus release jitter must stay within `VEHICLE_CL250_CLIENT_STEP_MAX_MS` (D-053).

./build/host-tests/src/vehicle_rtcore_host                  # simulated ECU, Ctrl-C to stop
./build/host-tests/src/vehicle_rtcore_host --vcan vcan0     # Linux
